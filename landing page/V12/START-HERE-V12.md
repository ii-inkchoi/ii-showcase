## 4. 확정된 규칙 (V12 는 이걸 그대로 물려받는다)

### 4-1. 제목 크기 — 자리마다 하나 (모바일 375 기준)

| 자리 | 값 | 예 |
|---|---|---|
| 히로 (페이지당 1) | **28** / 500 / 1.10 / −0.02em | "The market, every week," |
| 섹션 제목 (섹션당 1) | **28** / 500 / 1.10 / −0.02em | "The account is a container." |
| 항목 제목 | **22** / 500 / 1.25 / 0 | TFSA · "01 Answer the questionnaire" |
| 작은 항목 제목 (촘촘한 목록) | **17** / 500 / 1.30 / 0 | 뉴스룸 기사 줄 |
| 설명 · 본문 | **16 · 15 · 13** / 400 / 1.40 | |
| 숫자 (예외) | **34** / 500 / 1.15 / −0.069em | "9 in 10" · "−7.60%" |

> 데스크탑(1440)은 밴드형(홈·SD·Managed) = **48 / 28 / 22**, 콘텐츠 6 페이지 = **36 / 28 / 22**.

### 4-2. 두께는 두 개뿐 ★ 08-19 확정

> **제목은 500. 본문은 400.** 끝.

크기가 아니라 **역할**로 갈린다. 28·22·17 전부 500, 16·15·13 전부 400.

**왜** — 08-17 에 22 만 400 으로 정했었는데, 17 은 500 이라 크기가 **내려가는데 두께가 500 → 400 → 500 으로 튀었다.** 사다리가 자기 자신과 모순. 게다가 22 에서 400 과 500 은 나란히 놔도 거의 구분이 안 돼서, 400 은 보여주지도 못하는 예외를 사고 있었다.

**예외로 400 을 유지하는 것** — 제목이 아닌 것들. 히로 서브라인(`.hsub`), 노트(`.lnote`), 다크 페이오프 문장(`.qh2 .a/.b`). 크기가 22 여도 문장이면 400.

### 4-3. 행간도 사다리

| 크기 | 행간 |
|---|---|
| 28 | 1.10 |
| 22 | 1.25 |
| 17 | **1.30** |
| 16 · 15 · 13 | 1.40 |

**글자가 작아질수록 행간은 넓어진다.** 08-19 까지 17 이 1.15 였는데 22(1.25)보다 좁아서 사다리가 거꾸로였다. 두 줄짜리 17 제목이 밑의 설명문에 눌려 보였다.

### 4-4. 간격 사다리

| 값 | 쓰임 |
|---|---|
| **8 · 16** | 한 요소 **안**. 8 = 성격이 다른 두 가지를 붙일 때 (분류명 ↔ 날짜). 16 = 라벨 → 제목, 제목 → 설명 |
| **24** | 문장 사이 · 요소 사이 |
| **40** | 산문 → 카드/표/그림 (섹션 안) |
| **48** | 나란한 항목 사이 |
| **64 · 72** | |
| **104** | **비트 사이** |
| **208** | 섹션 경계 |

> ### ⚠ 104 를 두 번 잘못 썼다 (둘 다 인경 지적으로 교정)
>
> **104 는 비트 사이에만. 한 비트 안의 문단 사이에는 쓰지 않는다.**
>
> NO.02 의 카피 1·2·3 에 전부 104 를 넣었더니 자유롭게 떠 있는 블록 4 개가 됐다. 그 셋은 별개 아이디어가 아니라 **한 논증의 세 걸음**이다. 문단 사이는 **24**.
>
> 밴드 타이틀의 대구("solved access / never solved judgment")를 사진 위아래로 갈랐을 때도 같은 실수 — 문장 쌍이 아니라 별개 선언 두 개로 읽혔다. 되돌렸다.
>
> **간격을 정하기 전에 물을 것: 이 둘은 다른 아이디어인가, 한 아이디어의 다음 걸음인가.**

### 4-5. 선 (헤어라인) 규칙

- **바탕이 같은 두 섹션이 만나면** 선을 넣는다
- **바탕색이 바뀌면** 색 변화가 경계이므로 선을 넣지 않는다
- 콘텐츠 6 페이지는 위아래가 한 색 → 모든 이음매가 선을 받는다
- 선은 **화면 끝에서 끝** (375 기준 전폭). 그러려면 섹션이 화면 폭이어야 해서, `.container` 안에 든 섹션은 좌우로 빼냈다 (`margin:-20px` + `padding:20px`)

**긴 선이 안 맞는 경우도 있다** — manifesto 는 항목 높이가 206~501px 로 **2.4 배** 차이라 화면을 가로지르는 선이 그 불균등을 격자처럼 드러냈다. 인경: *"섹션마다 높이가 달라서 선이 있으니까 지저분해보여."* → 선 대신 **48 + 48 = 96 의 여백**으로 갈랐다.

### 4-6. 대문자는 13 티어에서 끝난다

> **대문자를 쓰는 곳은 13 모노 하나** — 섹션 아이브로우, 링크, 버튼.
> **11 과 9 는 대문자를 쓰지 않는다.** 예외는 **약자뿐** (`YTD` `FAQ` `CIRO` `CIPF` `TFSA` `RRSP` `S&P`).

**왜** — 대문자 모노는 "이건 읽는 글이 아니라 표시다" 라는 신호다. 한 크기에만 있어야 작동한다. 11 · 9 까지 번지면 페이지 절반이 표시가 되어 아무것도 표시하지 않는다. 그리고 11px 대문자는 짧을 때만 라벨로 읽힌다 — `TAX-FREE`(8자)는 라벨이지만 `SELF-DIRECTED INVESTING`(23자)은 읽기 힘든 문장이 된다.

**대문자를 푼 라벨은 Title Case 로 쓴다** — `Press Release` · `In the Press` · `Changelog`. 문장식(`Press release`)이 아니다. 이건 문장이 아니라 분류 이름이라서.

**날짜 자리표시자는 한 모양** — `[MMM DD], 2026`. 실제 날짜(`JUL 27, 2026`)와 골격이 같아 목록에서 줄이 안 흔들린다.

### 4-7. 표시(mark) 체계

| 표시 | 뜻 |
|---|---|
| ↗ | 화면을 떠난다 |
| `+` | 제자리에서 열린다 |
| 박스 | 그 자체가 어포던스 |
| 밑줄 | 문장 속 링크 |

manifesto 목록 표시는 **슬래시 `/`** (`c-600` #A7A7A7, 13 모노). 로고 `//` 에서 가져온 것 — 밖에서 빌려온 기호가 아니다.

### 4-8. 대표 기사 블록 (홈 · 뉴스룸 공통)

모바일 순서: **날짜/라벨 → 제목 → 이미지 → 요약 → READ**
간격: 라벨→제목 16 / 제목→이미지 24 / 이미지→요약 24 / 요약→READ 24

제목 크기는 **바로 위 제목보다 한 칸 아래**가 규칙이다. 절대 크기가 아니다.
- 홈: 위에 그룹 제목 `Press Releases`(22) 가 있으므로 기사 제목은 **17**
- 뉴스룸: 그런 그룹 제목이 없고 아래 목록 줄이 17 이므로 대표는 **22**

## 6. 함정 — 같은 실수를 반복하지 말 것

### 6-1. CSS 특이도 (제일 자주 걸렸다, 6 번 이상)

**공유 파일에 규칙을 썼는데 아무것도 안 바뀌면 100% 이것이다.**

페이지가 더 긴 셀렉터로 먼저 선언해놓으면 공유 파일이 진다. 실제로 겪은 것:

| 공유에 쓴 것 | 페이지가 선언한 것 | 결과 |
|---|---|---|
| `.lt-hd` | `.latest .lt-hd` | 안 먹음 |
| `.pflist .n` | `#portfolios .pfrow .n` | 안 먹음 (게다가 클래스 이름도 틀림) |
| `.loop3 .step .t` | `.loop3 .lstrip .step .t` | 안 먹음 |
| `.m-hero + .m-entry` | — | **형제가 아니라서** 안 먹음 |
| `.tbl th:first-child` | `.tbl.wide th:first-child` | 안 먹음 |

**규칙: 쓰기 전에 페이지가 그 속성을 어떤 셀렉터로 선언했는지 먼저 찾아라.** 그리고 쓴 다음엔 **반드시 브라우저에서 computed 값을 재라.** 파일에 썼다고 적용된 게 아니다.

### 6-2. 측정 프로토콜

```js
// 반드시 이 순서로
document.querySelectorAll('.ri,.rv').forEach(e=>e.classList.add('in'));   // 두 클래스 다!
const st=document.createElement('style');
st.textContent='*,*::before,*::after{transition:none!important}.ri,.rv{transform:none!important;opacity:1!important}';
document.body.appendChild(st);
// 그 다음 측정
```

- **`.rv` 만 풀면 안 된다.** 콘텐츠 6 페이지는 `.ri` 를 쓴다. 이걸 놓쳐서 pricing 항목 간격을 72 로 잘못 읽었다 (실제 48)
- **애니메이션이 도는 중에 재면 틀린다.** SD 아이브로우→제목을 48 로 잘못 읽고 그 위에 제안을 얹었다가 인경이 지적 (실제 24)
- **폭을 바꾸면 새로고침해야 한다**
- **캐시가 세다.** 주소에 항상 `?v=아무값` 을 붙일 것
- **추론해서 보고하지 말 것.** 실측하지 않은 보고는 번복된다

### 6-3. 주석 안에서 편집하면 `*/` 를 옮겨라 (세 번 반복했다)

주석 끝에 문단을 덧붙이면서 앞의 `*/` 를 안 지우면 **뒤의 산문이 CSS 로 파싱되어 그 아래 규칙이 조용히 죽는다.**

v11.css 를 고칠 때마다 측정 전에 균형부터 셀 것:

```bash
python -c "
import io;s=io.open('shared/v11.css',encoding='utf-8').read()
print('주석 %d/%d 괄호 %d/%d'%(s.count('/*'),s.count('*/'),s.count('{'),s.count('}')))"
```

### 6-4. HTML 엔티티가 대문자 검사를 통과시킨다

`RESEARCH &amp; ANALYSIS` 는 글자만 남기면 `RESEARCHampANALYSIS` 가 되어 소문자 `amp` 때문에 "대문자 아님" 으로 새어나간다. **엔티티를 먼저 풀고 판정.** 검사기는 고쳐놨다.

### 6-5. margin 이 쌓인다

한 이음매에 margin 하나만. 뉴스룸 대표 기사에서 플레이트 · `.rbody` · `.s` 가 각자 margin 을 가져서 이미지 밑 간격이 24 대신 **56** 이 됐다.

### 6-6. 모바일 그리드 리셋

데스크탑에서 `.row.feat .k{grid-column:7/span 2}` 같은 배치를 했으면, 모바일 1 칸 그리드에서 **전부 리셋해야 한다.** 안 하면 12 칸 배치가 살아남아 암묵적 컬럼이 생기고 이미지가 **0×0** 으로 무너진다. 데스크탑 규칙이 (0,4,0) 이라 일반 모바일 리셋 (0,3,0) 을 이긴다.

### 6-7. GitHub Pages — 밑줄 폴더 ★ 30 분 날림

**GitHub Pages 는 `_` 로 시작하는 폴더를 배포에서 뺀다.** `shared/v11.css` 가 404 가 나서 사이트가 오늘 작업 전부를 잃은 것처럼 보였다. 점으로 시작하는 파일(`.nojekyll`)도 같이 잘린다.

- `.nojekyll` 을 **리포 맨 위**에 두면 해결되지만, `ii-showcase` 는 첫 화면이 이미 Jekyll 사이트라 그러면 그쪽이 깨진다
- **그래서 배포본에서는 `shared` → `shared` 로 이름을 바꿨다**
- 폴더·파일 이름의 **공백**도 없앴다 (`v5 images` → `v5-images`, `video mobile` → `video-mobile`)

> **V12 결정 사항 #1 — 이 폴더의 `shared` 도 `shared` 로 바꿀 것인가?**
> 지금은 V11 원본 그대로 `shared` 다. 바꾸면 앞으로 배포할 때마다 이 문제가 사라진다. 안 바꾸면 매번 배포용 사본에서 고쳐야 한다. **바꾸는 것을 추천.** 작업은 폴더 이름 + HTML 9 개의 경로 문자열 하나뿐 (약 57 곳, 스크립트로 1 분).

### 6-8. 파일을 옮길 때 링크된 자산도 같이

6 페이지를 V11 로 복사하면서 그들이 링크하는 `mobile-canon.css` 를 빠뜨렸고, 그 상태로 한동안 측정했다.

### 6-9. OneDrive HTML 잘림

프로토타입 HTML 이 OneDrive 동기화로 조용히 잘린 적이 있다. 읽거나 고친 뒤 파일 끝에 `</html>` 이 있는지 확인할 것.

## 7. 일하는 방식 (인경과)

- **인경 = 디자이너.** 한국어/영어 혼용, 짧고 직선적. **답도 짧게.** 과한 설명 금지
- **중학생에게 설명하듯이. 모든 대화에서.** 전문용어 벽 금지, 뭐가 보이는지부터
- A/B 옵션을 보여줄 때는 **추천을 명시**
- **편집 전에 무엇을 바꿀지 먼저 보여주고 승인을 받는다.** "만들겠습니다"로 시작하지 말 것
  - 단, **명시적으로 요청된 변경은 재확인 없이 즉시 실행.** 게이트는 새 제안에만
- **커밋하지 않는다.** 이 작업 내내 커밋 요청은 없었다
- **판단이 필요한 부분은 무조건 홈 · SD 페이지 기준**
- **통일성이 최우선.** 한 페이지만 예외로 두는 해법은 기각된다
- 구조를 제안하기 전에 **실측 + 캡처**. 패턴 카탈로그에서 추론하면 번복된다
- **"Honestly", "Genuinely" 금지**

### 건드리면 안 되는 것

- **푸터 법무 문구** — 컴플라이언스 확답본. 디자인만 우리 것
- **SD / Managed 섹션 내용** — 컴플라이언스 제출본. 요소 삭제·추가·문구 변경 금지. "정리" 요청은 스타일만
- **웹 카피** — Dave 가 pressure-test 한 canon. 고치지 말고 플래그만
